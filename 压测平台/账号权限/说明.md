## 一、本轮边界

用户已明确授权执行第一份账号登录计划，已完成并通过本地验证；其余三份尚未执行。测试使用独立数据库／数据目录和缓存前缀，保留原8087实例；最新交付与证据以执行进度为准，不自动扩大到后续计划。

用户已明确：不做 SaaS 租户；一个账号可加入多个团队，团队下有多个项目；固定角色打包权限，不提供权限勾选和自定义角色；使用 Redis 保存登录 Token，返回前端写入 Cookie；提供无需登录的受限游客体验。

本次补充：项目增加“执行者”，具备只读能力并可执行已有压测场景；内置超级管理员 `admin`，初始密码 `admin`，首次登录强制改密，仅管理账号、全局角色分配及账号安全参数，禁止进入项目业务。Token 的 Cookie 名统一为 `deep_jmeter_token`，Redis 使用同名命名空间。失败登录达到可配置次数后锁定可配置分钟数。

会话只由 Redis Token 及用户 Token 索引管理；改密、重置、停用直接删除该用户全部 Token，退出仅删当前 Token。MySQL 不保存会话撤销版本。

补充要求：合适处优先使用设计模式；前端通过请求头传团队、项目编码，后端验证后形成包含用户标识的请求上下文，支持通过 `ThreadLocal` 读取。截图仅参考“左侧团队列表、团队项目页、成员与项目角色配置”的结构，不复制其中的企业、订单、套餐及真实业务数据。

前端 UI 必须以当前 deep-jmeter 已实现风格为主，TabTin Mac 客户端仅作样式细节参考。登录、团队、人员、邀请和游客页面统一复用当前配色、组件、密度及固定框架，不另起主题；具体约束与源码参考见[统一规范的界面章节](规划/账号与团队项目规范.md)。

登录方式、有效期、锁定参数默认值和具体游客限制仍是方案建议；本次用户指定的执行者、超级管理员边界、初始账号和 Token 键名作为明确要求。账号扩展仍须可移除，无账号核心继续完整可用。

第一计划交付见[账号登录验证记录](验证记录/2026-10-21-账号登录验证记录.md)，当前代码为 `codex/account-login / ba1413d`；第一计划通过不代表完整账号工作台已开放。

## 三、代码依据与共同交付要求

规划时基线：产品仓库 `/Users/yang/Documents/project/deep-jmeter` 的 `14222df`；当时已有项目隔离、卡片、场景／任务／报告和 `CapabilityService`，尚无账号体系。账号过滤器与 access／account 扩展目录已在第一计划新增；团队、项目成员和邀请仍待后续实现。

- 后端保持 Controller、Service 接口／实现、DTO／PO／VO 分层；SQL 全部使用 MyBatis XML，表和字段带中文 COMMENT。角色用固定枚举，不新增角色编辑器、权限配置表或审计中心。
- 实施前先保存当前项目工作台、列表、编辑器和确认弹窗的浏览器对照截图，列出复用控件；新页面按统一规范落地。各阶段附新旧页面截图对照，在 1440×900、1280×800、689×757 检查字体、配色、密度、滚动及状态，不能只凭功能测试通过就认定 UI 完成。
- 账号、团队、邀请是 MySQL 持久数据；Redis 仅保存可失效会话和限流缓存。报告缓存故障可回源，认证缓存故障不能放行私有数据。
- 账号扩展使用独立脚本和升级记录；改造当前 `SchemaUpgradeRunner` 的装配边界，未安装扩展时不扫描或校验扩展脚本。核心查询、执行和报告不依赖账号表。
- 将来确需重刷时，仅人工处理本项目 dev 库、升级记录和配套开发数据目录；先保留所需数据，禁止启动删库、修改摘要冒充升级或清空共享 Redis。本轮不执行重刷。
- 各计划验收后分别本地中文提交。后端执行 `mvn -f backend/pom.xml verify`，前端执行 `pnpm --dir frontend build` 与相应浏览器回归；提交前执行 `spotless:check`、`format:check`。无账号构建也须单独通过完整压测与导出回归，不推送、不发布。
- 回退使用上一版本程序及与其匹配的数据库、数据目录备份；不自动删扩展表。认证故障不能通过切换无账号模式回退，移除模块只能由部署者显式操作。
