## 一、本轮边界

本轮只编写规范与执行计划，不修改产品代码，不操作数据库，不重启当前前后端。下列计划均未执行；此前压测核心的开发授权不自动延伸到本轮账号开发。

用户已明确：不做 SaaS 租户；一个账号可加入多个团队，团队下有多个项目；固定角色打包权限，不提供权限勾选和自定义角色；使用 Redis 保存登录 Token，返回前端写入 Cookie；提供无需登录的受限游客体验。

补充要求：合适处优先使用设计模式；前端通过请求头传团队、项目编码，后端验证后形成包含用户标识的请求上下文，支持通过 `ThreadLocal` 读取。截图仅参考“左侧团队列表、团队项目页、成员与项目角色配置”的结构，不复制其中的企业、订单、套餐及真实业务数据。

登录方式、角色名称、有效期和游客限制是本方案建议值，尚未视为用户逐项确认。账号扩展仍须可移除，无账号核心继续完整可用。

## 三、代码依据与共同交付要求

核实基线：产品仓库 `/Users/yang/Documents/project/deep-jmeter`，提交 `14222df`。目前有项目隔离、项目卡片、场景／任务／报告和 `CapabilityService`；未实现本轮账号体系。过滤器、团队表和扩展目录等新增名称均是拟定设计。

- 后端保持 Controller、Service 接口／实现、DTO／PO／VO 分层；SQL 全部使用 MyBatis XML，表和字段带中文 COMMENT。角色用固定枚举，不新增角色编辑器、权限配置表或审计中心。
- 账号、团队、邀请是 MySQL 持久数据；Redis 仅保存可失效会话和限流缓存。报告缓存故障可回源，认证缓存故障不能放行私有数据。
- 账号扩展使用独立脚本和升级记录；改造当前 `SchemaUpgradeRunner` 的装配边界，未安装扩展时不扫描或校验扩展脚本。核心查询、执行和报告不依赖账号表。
- 将来确需重刷时，仅人工处理本项目 dev 库、升级记录和配套开发数据目录；先保留所需数据，禁止启动删库、修改摘要冒充升级或清空共享 Redis。本轮不执行重刷。
- 各计划验收后分别本地中文提交。后端执行 `mvn -f backend/pom.xml verify`，前端执行 `pnpm --dir frontend build` 与相应浏览器回归；提交前执行 `spotless:check`、`format:check`。无账号构建也须单独通过完整压测与导出回归，不推送、不发布。
- 回退使用上一版本程序及与其匹配的数据库、数据目录备份；不自动删扩展表。认证故障不能通过切换无账号模式回退，移除模块只能由部署者显式操作。
