## 3. 建议复用的 SQL

### 环境占用

```sql
SELECT COUNT(DISTINCT u.id) AS occupied_users
FROM account.user_info u
JOIN account.user_enterprise_pk r ON r.user_id = u.id
JOIN account.enterprise_info e ON e.id = r.enterprise_id
WHERE u.status = 1
  AND (u.username IS NULL OR BINARY u.username <> 'admin');
```

按有效企业关系去重，只按 username=admin 排除超级管理员，不按用户 ID。BINARY 是 MySQL 的精确大小写比较，实际 Mapper 按目标数据库使用等价写法；账号库名使用部署已有数据源，不硬编码 account。

### 企业统计

```sql
SELECT e.id,
       COUNT(DISTINCT u.id) AS member_count,
       COUNT(DISTINCT CASE
           WHEN u.status = 1
            AND (u.username IS NULL OR BINARY u.username <> 'admin')
           THEN u.id
       END) AS occupied_users
FROM account.enterprise_info e
LEFT JOIN account.user_enterprise_pk r ON r.enterprise_id = e.id
LEFT JOIN account.user_info u ON u.id = r.user_id
GROUP BY e.id;
```

从企业表开始保留零成员企业。单企业占用增加企业 ID 参数即可。实测全企业查询外层只返回汇总，未将真实企业名称或用户明细保存到文档。

## 4. 现有索引与执行计划

现有 `user_info` 有 id 主键、username/status/手机号/邮箱单列索引；`user_enterprise_pk` 有 user_id、enterprise_id 等单列索引；`enterprise_info` 有 id 主键。调整后的环境占用 JOIN 计划为：用户表 ref / index_pr_status（估计 9,501 行），关系表 ref / index_pr_user_id，企业表 eq_ref / PRIMARY；估计行数不是实际扫描行数。

当前查询已使用现有索引，暂不增加索引。列表按用户分页后批量查企业，避免 N+1 和关联放大；实现后用完整接口及导出复测耗时。
