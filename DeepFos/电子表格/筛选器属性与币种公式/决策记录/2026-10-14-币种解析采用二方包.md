# 币种解析采用二方包

> 状态：已确认
> 最后更新：2026-10-14
> 适用范围：ReqP_00486 的后端架构边界；不表示公共包已交付或所有发布细节已确认
> 关联文档：[主题说明](../说明.md)、[功能规范](../规划/功能与后端规范.md)、[二方包规范](../规划/币种解析二方包规范.md)、[实施计划](../代码执行计划/2026-10-14-筛选器属性与币种公式后端实施计划.md)

## 一、背景

用户明确自己只负责电子表格后端，维度和财务模型不在其源码负责范围。财务模型开发建议将币种解析做成二方包，让上层组件可以引入调用；用户授权可行性核对后直接更新规范。

此前方案默认在财务模型侧抽取并按需暴露币种解析入口，执行计划也列入了财务模型／维度源码改动。这一安排不符合当前职责边界，应由本决策替代。

## 二、核对依据

- 分类和映射逻辑可独立于金额、汇率及合并查询；模型关联、本位币和币种描述是宿主能够通过现有能力获取的数据。
- 电子表格已有模型元数据查询、维度批查以及 EntityCurrencyCheckService，不必为了币种标签新增远程业务接口。
- 两个服务均为 Java 21 的 Spring Boot 应用；整个财务模型应用包不适合作为轻量二方依赖。
- 两边已有规则副本并存在差异：电子表格包含 Consolidation 系列，财务模型包含 Contribution 系列和 AdjTotal，集合匹配策略也不同。共享规则及固定样例可避免新公式继续维护一份未经对齐的副本。

具体源码锚点见实施计划，公开包契约与验收见二方包规范。以上是源码证据，尚无已编译公共包或生产接入证据。

## 三、候选方案与决定

| 方案 | 取舍 |
| --- | --- |
| 复制财务模型规则到电子表格 | 首版方便，但其他上层继续复制，版本差异持续存在 |
| 财务模型新增远程解析入口 | 可以集中规则，但增加跨服务接入和他方源码改造，不作为用户当前交付安排 |
| 引入整个财务模型应用包 | 带入应用与运行时依赖，不能作为轻量公共库 |
| 独立普通 JAR，纯规则加宿主适配 | 本次采用；规则复用，数据查询、权限和批量继续由各上层负责 |

用户进一步确定 artifactId 为 `deep-currency-resolution`，工程形态为独立 Java／Maven 工程，并要求首版公开契约考虑其他组件复用；不将其实现为任一业务服务子模块。

采用本地两阶段调用：公共包先规划需要的数据，再用宿主提供的快照解析币种编码。公共包不持有 HTTP 客户端、Spring 容器、服务 DTO、RequestContext 或全局缓存。电子表格负责元数据及成员批查、描述和 DF 回填。

## 四、责任与后果

1. 用户负责电子表格公式和二方包接入，不默认修改维度或财务模型服务。
2. 二方包独立工程形态和 artifactId 已确定；实际仓库位置、groupId、首版版本、开发／发布及长期维护方由团队明确。若用户承接首版包实现，应明确独立交付物及发布职责；不能等同于财务模型服务改造。
3. 财务模型开发校验业务规则与新旧结构样例。其他上层接入及既有服务全面迁移不作为 ReqP_00486 首版前置。
4. 语义性规则变化需要发布新包并由消费方升级；维度配置变化通过新查询快照取得。纯规则包不是在线动态规则服务。
5. 与产品确认的 EC／PC／PT／指定币种口径、缺父级错误、无年版本参数和不执行金额计算的边界一致。

## 五、后续冻结项

架构选择、独立 Java 工程、artifactId=deep-currency-resolution 及跨组件通用设计要求已确认，以下交付细节仍需明确：独立工程的实际仓库位置、groupId、首版版本和最低 Java 版本、首版及长期维护方、规则差异／历史别名与旧结构样例、正式发布版本。它们不需要先修改财务模型或维度业务接口。
