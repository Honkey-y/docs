# 新增语言适配实施计划

> 状态：草稿
> 最后更新：2026-08-21
> 适用范围：`deepfos-platform` 合并后的 account、space、os-space、app、system、menu 和 platform-file 模块
> 关联文档：暂无

## 1. 文档目的

本文档用于在已合并的 `deepfos-platform` 项目中增加一种新语言，以合并前 7 个平台项目 `jdk21` 最新分支中的葡萄牙语适配为基准，给出当前合并项目的实际改动位置、执行顺序、数据库兼容要求和验收标准。

本文档的基线为：

- 当前合并项目分支：`feature_not_mult_login`
- 当前合并项目提交：`867fc9a27f1c67c5e3eff7cbc304463b06381f0d`
- 盘点日期：`2026-08-21`
- 旧项目本地分支均与对应 `origin` 分支一致，分支顶端均为 `2026-08-05` 的“未合并前 lts”提交。

> 注：目标语言尚未在需求中指定。本文统一使用 `<LANG_CODE>`、`<BUNDLE_SUFFIX>` 和 `<TARGET_TEXT>` 作为占位符，实施前必须先完成第 2 节的参数确认。

## 2. 实施前必须确认的参数

| 参数 | 含义 | 要求/示例 |
| --- | --- | --- |
| `<LANG_CODE>` | 系统内部语言代码 | 优先使用 ISO 639-1 小写代码，如 `ja`、`es`；全链路必须完全一致 |
| `<BUNDLE_SUFFIX>` | Spring MessageSource 资源文件后缀 | 单一语言通常与 `<LANG_CODE>` 相同；地区变体需确认 `xx_YY` 与 `xx-YY` 的映射 |
| `<LANG_NAME_ZH_CN>` | 语言的简体中文名称 | 如“日语” |
| `<LANG_NAME_ZH_TW>` | 语言的繁体中文名称 | 如“日語” |
| `<LANG_NAME_EN>` | 语言的英文名称 | 如 `japanese` |
| `<OS_USE>` | 平台是否对用户开放 | 完成翻译和验收后取 `1/true`；翻译未就绪时先取 `0/false` |
| 翻译口径 | 语种地区、专业术语和语气 | 明确地区变体、产品名不翻译清单、角色/组件术语表 |

语言代码长度还必须满足当前表结构：`sys_language_info.language` 最长 20，`role_name_des.language_code` 和 `element_category_language.language_code` 最长 10。

当前 6 份初始化 SQL 中已有下列语言元数据：

| 当前状态 | 语言代码 | 实施影响 |
| --- | --- | --- |
| 已开放且有完整平台资源 | `en`、`zh-cn`、`pt` | 通常不是本次“新语言”的目标 |
| 已有 79 个消息 key、95/73 JSON、8 个角色和 50 个元素类型翻译，但未开放 | `fr` | 如目标是法语，应做差距复核和启用，不要重复创建翻译资源 |
| 仅预置语言元数据，未开放 | `zh-tw`、`ru`、`de`、`es`、`ar`、`ja`、`he` | 不得再 `INSERT sys_language_info`；补翻译后通过新的 `UPDATE` 启用 |
| 完全不存在 | 除上述代码外 | 按全新语种路径新增元数据和全部翻译 |

因此，实施前的第一个技术门禁是确定目标属于以上哪一类。本文后续数量以“尚未拥有翻译的目标语言”为主；如目标是 `fr`，需改为差距复核、语言名称 API 修复和开放流程。

如需使用地区化代码（例如 `pt-BR`），不能直接按单语言代码方案实施。当前 3 个 `LocaleString` 实现只按下划线拆分 Locale，需先统一 HTTP 头、`RequestContext`、数据库代码、JSON key 和资源文件后缀，并改用 `Locale.forLanguageTag` 或增加明确的归一化逻辑。

## 4. 合并后的实际改动范围

合并后，account、space、app 和 system 的消息已集中到 `system-server/src/main/resources/i18n`，并由 `spring.messages.basename=i18n/messages` 统一加载。因此不应在各子模块重新创建独立资源包。

按“与葡语同等范围”实施时，当前项目的核心改动是 9 个文件：

| 类型 | 当前文件 | 执行改动 | 当前数量基线 |
| --- | --- | --- | --- |

6 份 SQL 对一个全新语言合计需新增 354 条目标语言 `INSERT` 语句。如 `<LANG_CODE>` 已预置在 `sys_language_info` 中，则不再增加该表的 6 条 `INSERT`，而是每种方言新增一条明确的 `UPDATE`；最终数据库行数门禁仍为 1/8/50。应以当前合并项目的葡语/法语数据集为模板，不应直接复制 2025 年历史提交，因为当前 `module_language.json` 已从旧项目的 80 个对象增长到 95 个。

### 4.1 不需直接改动的模块

按葡语基线，以下模块不新增目标语言专属文件：

- `os-space-tenant`：使用平台/空间语言配置，需联调新语言启用和默认语言回退。
- `menu-server`：菜单描述以 `Map<String,String>` 动态传递，需验证目标 key 有值时的查询和缓存。
- `platform-file-server`：只向下游透传 `RequestContext.getLanguage()`/请求头，需验证语言代码不丢失。

## 5. 分文件实施说明

### 5.1 新增统一消息资源包

新建：

```text
system-server/src/main/resources/i18n/messages_<BUNDLE_SUFFIX>.properties
```

执行要求：

1. 以当前 `messages_pt.properties` 的 79 个 key 作为“葡语等价范围”的直接基线，不得改动 key。
2. 保留 `{0}`、`{1}`、`${loginTime}`、`${product}` 等所有参数占位符，数量和名称必须与源文一致。
3. 保留 HTML 结构、`\n`、引号和反斜线转义；对通知邮件至少做一次实际渲染。
4. 项目已配置 `spring.messages.encoding=utf-8`，可使用 UTF-8 原文；如团队继续使用 `\uXXXX` 风格，必须全文一致且能正确反解析。
5. 不得出现重复 key、空翻译、翻译后的 key 或意外换行。

当前 `messages_en.properties` 有 88 个 key，比中文/葡语/法语多 9 个 `11370001`~`11370009`，且存在 `import.role` 与 `import.role.code` 的历史差异。严格对齐葡语时可保持 79 个 key；如本次要求“完整覆盖当前全部已知消息”，应先由开发确定唯一的 canonical key 集合，再对所有语言一并补齐，不要只让新语言拥有额外 key。

### 5.2 补齐组件和元素 JSON

修改：

```text
system-server/src/main/resources/module_language.json
system-server/src/main/resources/module_element_language.json
```

在每个 `desc` 对象中新增：

```json
"<LANG_CODE>": "<TARGET_TEXT>"
```

执行要求：

- `module_language.json` 必须覆盖当前全部 95 个对象。
- `module_element_language.json` 必须覆盖当前全部 73 个对象。
- 不修改 `id`、`type` 及其他语言的值，除非另有明确缺陷单。
- DeepModel、DeepPipeline、MySQL、Oracle、Python、BI、UX 等产品/技术名称按术语表保留。
- 重复的中文/英文名称也必须按每个独立 `id` 填充，不能因去重而漏项。

### 5.3 补齐 6 种数据库初始数据

每个 SQL 文件补齐下列三组数据。在动手前，先在当前 SQL 中查询 `<LANG_CODE>`，分别确认三张表中是“不存在”、“已存在但未启用”还是“已完整适配”。

#### A. `sys_language_info`

如 `<LANG_CODE>` 完全不存在，每份 SQL 增加 1 条：

```sql
INSERT INTO sys_language_info
VALUES ('<LANG_CODE>', '<LANG_NAME_ZH_CN>', '<LANG_NAME_ZH_TW>', '<LANG_NAME_EN>', <OS_USE>);
```

PostgreSQL 使用 `true/false`，其他当前脚本使用 `1/0`。列顺序必须与当前表结构一致。

如 `<LANG_CODE>` 已是预置行，保留原有 `INSERT`，并在翻译块后新增独立的幂等 `UPDATE`，用于同时覆盖新装和存量库：

```sql
UPDATE sys_language_info
SET zhcn_name = '<LANG_NAME_ZH_CN>',
    zhtw_name = '<LANG_NAME_ZH_TW>',
    en_name = '<LANG_NAME_EN>',
    os_use = <OS_USE>
WHERE language = '<LANG_CODE>';
```

不要只把原有 `INSERT` 中的 `os_use=0` 改成 `1`。初始化服务按 SQL 完整文本判断是否已执行；存量库会把改过的 `INSERT` 视为新语句再次执行，导致主键冲突。

#### B. `role_name_des`

每份 SQL 增加 8 条，角色 ID 必须完整覆盖：

```text
-8, -7, -6, -5, -4, -3, -2, -1
```

分别对应空间消息管理员、应用开发者、元素使用者、企业管理员、应用成员、应用管理员、空间成员管理员、空间管理员。

#### C. `element_category_language`

每份 SQL 增加 50 条，元素类型必须完整覆盖：

```text
ACCOUNTING, ACCOUNTING_EVENT_TYPE, ACS, BCF, BCUB, BCUBVIEW, BF, BID, BILL,
CHT, COG, CON, CONN, CS, CUB, DATASOURCE, DAT_CLICKHOUSE, DAT_DEEPENGINE,
DAT_DEEPMODEL, DAT_KINGBASE, DAT_MYSQL, DAT_ORACLE, DAT_SQLSERVER, DIM, DPL,
DS, GR, GRD, IMFM, IMS, INDI, JF, JL, JM, JR, JT, LST, MAINVIEW, MEN, MPT,
MR, MS, PCS, PY, RECON, RR, SML, VAR, WKFL, WP
```

数据库执行注意事项：

1. 先在 MySQL 脚本完成内容对齐，再按当前 5 份脚本的方言风格同步，禁止用文本盲替换覆盖整段 SQL。
2. 目标语言中的单引号必须按对应数据库方言转义；不能直接复制 MySQL/OceanBase 的反斜线转义到 PostgreSQL 系脚本。
3. `role_name_des.value` 和 `element_category_language.value` 当前为 `varchar(100)`，翻译定稿前要检查长度。
4. 当前 `InitServiceImpl` 会把 SQL 拆成单条内容，并通过 `init_sql_content` 记录跳过已执行语句。新增的 `INSERT` 会在已有环境下被识别为新内容并执行，因此这 6 份初始化 SQL 同时承担新装和存量环境补数。
5. 上线前要查询目标环境是否已预置或手工插入同一 `<LANG_CODE>`。如存在，使用经评审的 `UPDATE`/幂等策略，避免主键冲突被初始化逻辑仅记录为失败后继续启动。
6. 不得为了补数手工重跑脚本中的 `truncate` 语句。存量库只执行新增的目标语言语句。

### 5.4 语言名称 API 的必选决策

当前 `LanguageNameEnum` 只包含 `zh-cn`、`zh-tw`、`en`，而 `sys_language_info` 也只有 `zhcn_name`、`zhtw_name`、`en_name` 三个名称列。葡语历史改动没有扩展这一层，所以当请求上下文语言为 `pt` 时，`os-language-list` 的 `name` 可能为空，`os-language-name` 可能报“不支持该语言名称描述”。

新语言上线前必须在下列方案中明确选择一个：

1. **推荐：目标语言界面下，语言列表名称回退到 `en_name`**。修改 `system-server/src/main/java/com/proinnova/system/language/enums/LanguageNameEnum.java`，为 `<LANG_CODE>` 显式映射 `en_name`，或将未知界面语言统一回退到 `en_name`；同时增加 service/mapper 测试。
2. **扩展方案：语言名称也使用目标语言显示**。需扩展 `sys_language_info` 表列、6 种数据库 DDL/DML、`LanguageNameEnum` 和所有存量数据。该方案超出历史葡语改动范围，必须单独评审。

如只要求“完全复刻葡语改动范围”，可不修改 Java，但必须在验收报告中明确记录上述空名称/异常行为；不建议带着该已知缺口开放 `<OS_USE>=1`。

## 6. 执行顺序

1. **锁定语言规格**：确认第 2 节所有参数、地区变体、术语表和 `OS_USE` 策略。
2. **导出翻译清单**：分别从 79 个消息 key、95 个组件对象、73 个组件元素对象、50 个元素类型和 8 个角色生成翻译表。
3. **翻译与审校**：优先翻译产品术语、角色、组件/元素名称，再翻译错误信息和 HTML 通知；专业人员审校后冻结文案。
4. **改消息包和 JSON**：先完成 1+2 个资源文件，通过 key/占位符/JSON 覆盖检查。
5. **改 6 份 SQL**：以当前 MySQL 中的葡语块为数据集模板，再逐份按方言适配，通过 1/8/50 计数门禁。
6. **处理语言名称 API 决策**：如采用英文回退或扩展列方案，完成对应 Java/SQL/测试。
7. **静态校验和构建**：执行第 7 节命令，确保资源文件进入最终 JAR。
8. **新装+存量联调**：新数据库验证完整初始化；已有数据库验证新 SQL 通过 `init_sql_content` 补入且无失败记录。
9. **功能验收后开放**：仅在验收通过后把 `<OS_USE>` 设为 `1/true`，并通知前端/网关使用相同语言代码。

TARGET_LANG_CODE='<LANG_CODE>'

### 7.1 消息 key 数量与重复检查

```bash
awk -F= '/^[^#![:space:]][^=]*=/{n++} END{print n+0}' \
  "system-server/src/main/resources/i18n/messages_${TARGET_BUNDLE_SUFFIX}.properties"

awk -F= '/^[^#![:space:]][^=]*=/{print $1}' \
  "system-server/src/main/resources/i18n/messages_${TARGET_BUNDLE_SUFFIX}.properties" \
  | sort | uniq -d
```

第一条在葡语等价范围下应输出 `79`，第二条应无输出。还需对每个 key 比对 `{n}`、`${name}` 占位符集合，不能只比较 key 数量。

### 7.2 JSON 语法与覆盖检查

```bash
jq empty system-server/src/main/resources/module_language.json
jq empty system-server/src/main/resources/module_element_language.json

jq --arg code "$TARGET_LANG_CODE" \
  '[.[] | select(.desc[$code] == null or .desc[$code] == "")] | length' \
  system-server/src/main/resources/module_language.json

jq --arg code "$TARGET_LANG_CODE" \
  '[.[] | select(.desc[$code] == null or .desc[$code] == "")] | length' \
  system-server/src/main/resources/module_element_language.json
```

两个覆盖检查均应输出 `0`；两份文件的对象总数应分别为 `95` 和 `73`。

### 7.3 SQL 数量检查

每份 SQL 最终初始化后，目标语言在数据库中应有：

- `sys_language_info`：1 条。
- `role_name_des`：8 条。
- `element_category_language`：50 条。

对一个全新且尚未翻译的代码，可先用文本计数做静态检查：

```bash
for sql_file in system-server/src/main/resources/SYSTEM-INIT/{dm,kingbase8,mysql,oceanbase,opengauss,postgresql}.sql; do
  printf '%s\n' "$sql_file"
  rg -c "sys_language_info.*'${TARGET_LANG_CODE}'" "$sql_file"
  rg -c "role_name_des.*'${TARGET_LANG_CODE}'" "$sql_file"
  rg -c "element_category_language.*'${TARGET_LANG_CODE}'" "$sql_file"
done
```

如目标是已预置或已翻译语言，文本命中数会包含原有 `INSERT` 和新增 `UPDATE`，不能把“命中行数”当成“最终数据行数”。必须在实际新装库和存量库中用 `WHERE language/language_code='<LANG_CODE>'` 查询验证 1/8/50。

所有路径都必须比较 6 份 SQL 的角色 ID 集合和元素类型集合，确保不是“数量相同但 ID/type 错位”。

## 8. 功能验收清单

### 8.1 平台与空间语言

- `POST /language/os-language-list` 能返回 `<LANG_CODE>`，并且 `osUse` 与配置一致。
- 在请求上下文为 `<LANG_CODE>` 时，语言列表 `name` 不为空；`GET /language/os-language-name` 行为符合第 5.4 节已选方案。
- 新空间能从平台启用语言中初始化 `<LANG_CODE>`，已有空间能选中/取消选中该语言。
- 当请求了平台未启用的语言时，空间默认语言回退行为不变。

### 8.2 消息资源

至少各选一个代表 key 做真实请求：

- system：`11010001`，验证 `{0}` 参数。
- space：`12080001`，验证 `{0}`、`{1}` 参数。
- app：`13210001`。
- account：`import.space.name`、`sys.role.default_admin`。
- 通知：`title.deep_login_notice`、`content.deep_login_notice` 及 license 通知，验证 HTML 和 `${...}` 占位符渲染。

所有场景都不得返回 `[key]`、空文本或意外回退到系统默认语言。

### 8.3 组件、元素、角色与菜单

- 组件列表/安装信息中的 95 个组件名称可按 `<LANG_CODE>` 查取。
- 组件元素名称可按 `<LANG_CODE>` 查取，随机抽查不少于 10 种且覆盖带 Beta/版本号/数据库名的项。
- 8 个系统预置角色均显示目标语言，不得出现角色 ID 与名称错位。
- 50 个元素类型均有目标语言行。
- `menu-server` 在菜单 `languageInfo` 包含 `<LANG_CODE>` 时能返回正确的 `currentDescription`，且切换语言后缓存 key 隔离正常。

### 8.4 数据库新装和升级

- 新装环境：三张表中 `<LANG_CODE>` 行数分别为 1、8、50。
- 存量环境：启动后自动补入同样数量，`init_sql_content` 中没有该语种 SQL 的 `FAIL` 记录。
- 重启环境：不重复插入，不产生主键冲突日志。
- 至少完成 MySQL/OceanBase 系和 PostgreSQL/openGauss 系各一个真实库验证；其他方言完成脚本语法和转义检查。

### 8.5 透传联调

- `platform-file-server` 向下游请求透传的 `language` 头等于 `<LANG_CODE>`。
- `os-space-tenant`、space、app、system、menu 之间的内部调用不丢失语言上下文。
- 切换中文、英文、葡语和新语言后，各语言数据/缓存不串扰。

## 9. 严格葡语等价范围之外的已知缺口

历史葡语改动只覆盖资源和初始数据，没有清理全项目中所有“中文/英文二选一”的硬编码。当前合并项目仍有如下类型的热点：

- account 的 `LogContentEnums` 及部分导入/日志信息。
- app 的 `SpModuleOperateNoticeConfigManage`、`ElementInfoServiceImpl`、`JobServiceImpl` 等，部分场景不是中文就回退到英文。
- system 的 `SysSpaceServiceImpl`、`MessageManageService`、`UserRoleLogContentEnums` 等。
- menu 的部分历史数据兼容逻辑只构造中文/英文描述，目标 key 缺失时可能返回空值。
- job/log 的 `LanguageLogContentEnum` 只定义 `zh-cn`、`zh-tw`、`en`。

如产品定义的“适配新语言”包含全部操作日志、导入导出、作业状态、菜单历史数据和所有异常消息，必须将这些热点作为第二阶段全量国际化专项，不能宣称“仅完成上述 9 个文件就实现全平台 100% 翻译”。

本次如严格按葡语历史范围执行，上述热点只做回归测试和缺口记录，不纳入 9 个核心文件改动计数。
