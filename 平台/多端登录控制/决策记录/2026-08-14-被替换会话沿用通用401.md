# 被替换会话沿用通用401决策

> 状态：已确认
> 最后更新：2026-08-17
> 适用范围：`mode=3` 会话替换后的旧 token 鉴权失败处理
> 关联文档：[禁止多端登录实施计划](../代码执行计划/2026-08-14-禁止多端登录实施计划.md)

## 1. 背景

前期方案曾考虑为被新登录替换的旧 token 保存带 TTL 的失效原因墓碑，并由账号服务、Gateway 和前端通过 `SESSION_REPLACED` 区分“被挤下线”和普通登录失效。

产品最终确认：被替换用户不需要弹窗、Toast 或专用提示，因此没有必要继续区分失效原因。

## 2. 决策

1. `mode=3` 新会话替换成功后，直接删除旧 `ACCOUNT_TOKEN_{oldToken}` 和 `{oldToken}|tokenListener`。
2. 不保存旧 token 墓碑、剩余 TTL、历史集合或 ZSet。
3. 不增加 `SESSION_REPLACED`、`reasonCode`、响应头或专用错误文案。
4. 不修改账号服务现有 401 body，不修改 Gateway 的通用 401 转换逻辑。
5. 旧 token 后续访问与主动退出、自然过期等无效 token 一样，沿用当前系统已有的通用 HTTP 401 和前端登录失效处理。

## 3. 保持不变的相关需求

- 主 `POST /oauth/login` 已有有效会话时，仍通过登录 VO 的 `needConfirmReplaceSession` 让当前登录用户确认是否替换。
- 用户确认后携带 `confirmReplaceSession=true` 重试完整登录请求。
- `/oauth/login/password`、SSO/OAuth 等非主登录入口不增加确认交互，按 `mode=3` 自动替换。
- 实际替换成功后，仍向当前登录账号发送“已替换其他会话”站内信；模板编码为 `deep_single_login_notice`，DML 和正文以实施计划 6.4.2 为准。

## 4. 影响

### 4.1 收益

- 删除墓碑 TTL、专用异常、双层鉴权改造、Gateway 透传和前端被挤提示，改动范围显著缩小。
- 不新增 Redis 敏感会话历史数据，也不存在墓碑清理和 TTL 对齐问题。
- Gateway 无需随账号服务联动发布。

### 4.2 接受的限制

- 系统无法从 401 响应判断 token 是被新登录替换、主动退出还是自然过期。
- 被替换用户只看到现有通用登录失效行为，不会获知具体退出原因。

上述限制已由产品确认接受。

## 5. 验证要求

- 删除旧 token 后，经 Gateway 访问业务接口仍返回改造前已有的通用 401。
- 删除旧 token 后，直接访问账号受保护接口仍返回账号改造前已有的通用 401。
- 响应不新增 `reasonCode` 或专用文案，前端不新增被挤提示。
- Redis 不产生旧 token 墓碑或历史记录。
