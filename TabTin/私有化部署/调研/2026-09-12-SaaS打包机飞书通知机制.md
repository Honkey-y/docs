# SaaS 打包机飞书通知机制

核查日期：2026-09-12。范围：源码、旧 SaaS 打包机实际配置与运行进程、飞书官方文档入口。只读调研，没有发测试消息，没有改服务或重启进程。

## 结论

当前 SaaS 打包机通过飞书群自定义机器人的 Webhook 发送打包生命周期卡片。它是控制台代码触发的 HTTP POST，PM2 负责提供机器人地址并保持控制台在线。与私有机用于身份认证的 SSH 隧道是两条独立链路。

```text
用户在 SaaS 控制台开始打包
  → 控制台向 Runner 提交任务
  → 取得任务 ID 后发送“打包开始”卡片
  → 控制台每 2 秒查询执行状态
  → 同一任务从 running 变为 success / failed
  → 发送“打包成功 / 失败”卡片

通知出口：控制台 → HTTPS POST → 飞书群自定义机器人 → 对应群聊
```

接收目标是 Webhook 所属群，当前卡片没有按姓名分发、私聊用户或 @指定人的逻辑。“有些人收到”通常与这些人是否在目标群、是否开启群通知有关。触发人姓名只是卡片展示字段，不是消息收件人。此次没有读取飞书群成员或个人通知设置，因此不能确定具体群名、成员名单以及每个人是否弹出提醒。

## 消息内容与发送方式

| 阶段 | 卡片样式 | 内容 |
| --- | --- | --- |
| 接单后 | 蓝色“开始” | 执行机、目标分支、版本、触发人、环境、任务 ID、时间、记录链接 |
| 成功 | 绿色“成功” | 上述信息、耗时；客户端任务有产物时显示下载按钮 |
| 失败 | 红色“失败” | 上述信息、错误摘要、记录链接 |

发送载荷为 msg_type=interactive 和 card 对象，卡片 schema 为 2.0；每个阶段发一条新消息，当前没有根据 message_id 更新上一条卡片的流程。卡片配置中的 update_multi 不意味着程序已实现持续编辑或进度刷新。

本通道不需要按收件人查询 open_id，也没有获取 tenant_access_token 的调用；Webhook 本身定位机器人和群。当前请求未见 timestamp/sign 签名字段，群端安全设置没有在本轮核查。

## 另一条备用通知通道

notify.mjs 还保留 lark-cli 通知：notify.enabled 开启或请求带 messageId 时，在完成后向 chatId 发摘要和日志文件，或回复指定原消息。默认身份是 bot。此能力与 Webhook 卡片独立；当前全局配置关闭，但任务请求仍可显式选择消息回复。

所以如果以后要“只通知发起人”，应单独设计应用机器人私聊的用户映射及权限；当前群 Webhook 不会因为填了触发人名字就给该人私聊。

## 验证与边界

本地运行 node --test test/test-deploy-feishu-card.test.mjs（模块目录内）验证卡片组装与模拟请求；所有发送测试使用替代 fetch，没有向真实群发消息。7 项通过。

- 发送异步执行、超时 10 秒，失败只记日志；未发现持久重试队列，网络错误可能漏通知。
- 结束通知依赖内存中的状态变化：控制台中途重启，或极短任务未被轮询捕获 running 状态，可能漏掉结束卡片。这是源码推断的边界，本轮未在真实任务上触发。
- 卡片中的日志、下载链接来自 PACK_CONSOLE_PUBLIC_URL。当前部署配置缺省是局域网地址，收到飞书消息不代表在外网能打开这些链接。
- 私有打包机接入同类通知需要增加任务事件调用与机器人配置；本次没有改私有打包机通知逻辑。
