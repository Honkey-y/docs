## 先亲手完成这个练习

前提：账号可使用模型和 TabDoc。练习中的名称都是新建的学习资料。

1. 在“任务”入口提交：
   > 请创建一篇名为“我的入职学习清单”的 TabDoc。把“体验一次任务、读懂核心概念、跟通一个后端接口”整理成三个步骤，每步加一个完成标准。
2. 查看执行过程；出现权限请求时，阅读对应操作并决定是否允许。
3. 打开生成的文档，手动修改一行。
4. 关闭后重新打开，确认修改仍在，再回到任务补充一条要求。

验收四件事：**文档存在、内容符合要求、能手动修改、重开后内容仍在。**

如果没有创建成功，记下失败步骤和错误；若提示没有可用模型，先核对账号或本地模型配置。具体按钮名称以安装版本为准。

## 第一个后端接口：查询我参与的项目

这个例子适合入门，因为它能串起登录身份、组织范围、成员权限和分页。

已核对的请求路径：

```http
GET /api/context/projects?organization_id=<当前组织ID>
Authorization: Bearer <当前登录令牌>
```

只使用自己的登录态和可访问组织。以下是阅读顺序：

| 顺序 | 实际代码入口 | 阅读时回答一个问题 |
| --- | --- | --- |
| 1 | [tabtin/urls.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/tabtin/urls.py) 和 [routers/__init__.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/apps/tabtinspace/routers/__init__.py) | `/api`、`/context`、`/projects` 怎样拼成完整路径？ |
| 2 | [routers/project.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/apps/tabtinspace/routers/project.py) 的 `list_projects` | 登录用户、组织参数和分页从哪来？ |
| 3 | [services/project_service.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/apps/tabtinspace/services/project_service.py) 的 `list_projects` | 怎样只查当前组织中自己有效参与的项目？ |
| 4 | [models.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/apps/tabtinspace/models.py) 的 `Project`、`ProjectMembership` | 项目和成员关系怎样存？ |
| 5 | 回到路由的 `_serialize_project` 和 `success_response` | 数据怎样转成前端使用的响应？ |

这里能看到真实边界：查询会过滤已归档、已删除的项目；项目功能未开放，或缺少组织参数时，当前列表接口返回空列表。**空列表本身不能证明数据库里没有项目。**

对应边界测试可读 [test_project_feature_flag.py](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin_django/apps/tabtinspace/tests/test_project_feature_flag.py)。先读断言，看它保护了什么行为。

## 你现在使用的轻量环境

你通过 `bash dev.sh` 的菜单 **35** 启动，数据库、Redis 等使用 test。它有两种运行方式：

| 配置 | 本机跑什么 | test 跑什么 |
| --- | --- | --- |
| 未启用本地 Django | Electron 客户端 | API、数据库、Redis、协作、推送和异步服务 |
| `TABTIN_LITE_START_DJANGO=1` | Electron、Django、Collab | 数据库、Redis；推送和异步服务默认仍在 test |

**本次核对你机器上的开关是 `1`，属于第二种。** 因此你可以调试本地 Django 和协作代码，数据仍使用 test；也不需要为了熟悉产品改用菜单 1。

仓库根 `.env` 是基线，`.env.local` 是个人覆盖。菜单 35 还会设置启动进程的 API / 协作地址，所以不能只凭一个配置字段判断实际请求发到哪里。

已经正常运行就继续使用。需要手动启动时，在仓库根目录执行：

```bash
bash dev.sh
# 选择菜单 35
```

你当前这类本地 Django + Collab 环境可检查：

```bash
curl -sf http://127.0.0.1:6060/health
curl -sf http://127.0.0.1:4100/health
```

分别应看到健康状态 `healthy` 和 `ok`；本次只读检查已通过。它们证明服务就绪，功能是否成功还要回到客户端验证。

**本地代码和远端代码分开生效。** 本地 Django 改动需要重启本地服务；test 上的 Celery worker、IM 等服务不会自动运行你本地改过的代码。共享 test 也不等于独立测试库。

AI 必须重启客户端时，使用持久终端并保持相同 API / 协作路由，步骤见 [harness 环境与启动](/Users/yang/Documents/larchiveai/TabTin/harness/环境与启动.md)。

## 做第一个需求时记住这些

- **改 API 要兼容已发布客户端。** Electron、iOS、Android、CLI 都可能调用它；检查请求参数和响应解析。
- **本地 Django 改动后要重启再验证。** 它不会自动热重载；异步任务改动要在实际消费任务的 worker 上生效。本地重启不能更新 test 上的 Celery 代码。
- **看当前分支与现场。** 提交走工作分支 → 目标 `release/*` 的 PR；目标发布分支以当时仓库约定为准。
- **按真实流程验收。** 同时看用户操作、实际数据和失败场景；后端测试默认用本地 PostgreSQL。

重启命令、Electron 启动方式和提交规则以 [仓库工作说明](/Users/yang/Documents/larchiveai/TabTin/AGENTS.md) 为准。以后让 AI 开发或修 bug，先让它读 [harness 入口](/Users/yang/Documents/larchiveai/TabTin/harness/README.md)，按要求先用 CodeGraph 定位代码，再动手。

把负责模块、带教 / 评审人、测试账号和第一个需求确认下来，就可以围绕真实工作继续深入。
