## 本次范围和取舍

- 复用现有独立开发 worktree，不改主目录其他任务现场。控制台单进程调度两个持久构建 clone；计划解析使用独立源码 clone。

## 后续定位：新分支停在拉取源码

### 已确认事实

- 任务于 **17:32:13** 开始。排查初期 worker、`git fetch`、SSH 和 `git index-pack` 均存在；未进入依赖安装或 ARM 编译。
- 实际命令是 `git fetch --no-tags origin private/260907-build-opt`，SSH 连接目标 `ssh.github.com:443`。`index-pack` 的包头显示 **282,666 个对象**。
- 临时包收到 **132,677,631 字节（约 126.5 MiB）**，最后写入时间 17:39:00。任务在 **17:39:16** 自行记录 `failed` / Git 退出码 128，源码锁已释放。之后临时包大小不变是失败残留，不能据此误判仍有活进程卡住。
- 最终日志明确为：

```text
Connection to ssh.github.com closed by remote host.
fetch-pack: unexpected disconnect while reading sideband packet
fatal: early EOF
fatal: fetch-pack: invalid index-pack output
```

- 新建只读 `git ls-remote` 连接 **9.36 秒成功**，说明分支存在、凭据可用；该次查询看到分支已推进为 `bce8bf4f872f42f02349925e617116b6496a169d`。这不改变失败任务原本确认的 `800b8e9b…`。
- 计划 clone 已经有 `800b8e9b…`，构建 clone 尚未拥有该提交，仍再次从 GitHub 获取。代码路径为 `checkoutPlanSource()` → `fetchRef()` → `run()`。
- 构建 clone 是浅克隆，fetch refspec 只有 `+refs/heads/codex/private-pack-machine:refs/remotes/origin/codex/private-pack-machine`；只有两个该分支引用，没有 private 分支跟踪引用。当前 detached HEAD 可达 6,415 个提交，但本地 codex 分支引用仅可达一个提交。
- 两个既有约 340 MiB 的 pack 分别含 293,155 与 293,150 个对象，其中 **293,150 个完全重叠**，证明此前已有大量重复拉取/存储，不能把整个问题解释为新分支首次正常下载。
- `fetchRef()` 未传 `--progress`，子进程 stderr 为管道；因此日志长时间只有“正在拉取源码”。SSH 实际 `ServerAliveInterval=0`，代码只有连接阶段的 `ConnectTimeout=15`，没有传输阶段的保活/无进展超时。

### 结论与修复方向

直接失败原因是 **GitHub SSH 数据传输意外断开**，不是 ARM 架构编译错误或两个构建槽互相抢锁。没有足够证据把断链进一步归责为 GitHub 服务端、VPN 或其中某一段网络；不能仅凭错误文字断言某一方故障。

同步实现还有可修复的低效与可观测性缺口：生成计划已下载提交，执行任务仍无条件外网 fetch；单分支浅克隆和不完善的引用保留伴随大范围重复对象；没有显示进度或及时识别断流。此前双路实测使用已经缓存的固定 SHA，没有覆盖本次切换到新分支的冷同步情形。
