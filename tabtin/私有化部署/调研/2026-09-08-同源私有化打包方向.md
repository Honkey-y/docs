## 用户目标与结论

目标：从当前 SaaS 发布源码打包私有化版本，在打包页面选择腾讯 IM 或自研 IM、阿里云 OSS 或本地存储，避免长期维护客户功能分支并反复合代码。服务器希望最终交付单镜像；桌面客户端是否可以单独提供 DMG/EXE，需要明确。

结论：方向可行。建议让“同一份源码 + 一份交付配置”生成服务器制品和桌面制品。桌面应用独立安装到员工电脑，无须运行在服务器镜像中。若必须交付真正的单镜像，应将其作为服务端的一种装配方式，而不把桌面应用或平台构建工具强行放入运行镜像。

这次新增了客户分支证据，补充并限定[上一轮调研](2026-09-08-服务部署现状.md)：上一轮关于腾讯主链和 Docker 缺口的结论仅对应当前 SaaS checkout，不能代表客户分支。

## 1. 两条线实际有什么

| 能力 | SaaS 当前源码 | 客户分支 |
| --- | --- | --- |
| IM | `IMProviderId='tencent'`；Registry 显式拒绝非腾讯实现；桌面主进程运行腾讯 SDK，渲染层通过远程 Provider 接入 | `IMProviderId='django'`；`createDjangoIMProvider` 访问 Django `/api/im`。即已有 Django 自研实现，不是另一套独立 Go IM |
| 存储 | `SERVICES_OSS_PROVIDER` 工厂支持 `local` 和 `aliyun` | 保留同一工厂，但 Community edition 明确拒绝非 `local`，不能直接用 edition 开关实现任意 IM/OSS 组合 |
| 短信、邮件 | 默认选择云服务提供方 | Compose 设为 `disabled`，邮件使用 console backend；固定验证码单独控制，不应当作企业认证方案 |
| 版本识别 | 当前未找到客户版这组 edition/distribution 配置 | 有 `TABTIN_EDITION=saas/community`、桌面 `DistributionProfile` 和 Community 打包配置 |
| 服务编排 | 普通 deploy Compose 15 服务 | `compose.yaml` 声明 5 服务、4 种镜像：PG、Redis、Django、Celery、Centrifugo。不是单镜像 |
| 客户端打包 | `build-packaged-app.sh` 允许 local/preprod/production；网关 stable 渠道映射 production | 允许 local/community，有 `build:mac:community`、`build:win:community`，输入企业服务端点，可关闭自动更新 |
| 页面打包 | `tools/tabtin-pack-gateway` 提供 Console/Runner、客户端打包和 ACK 发布 | 该内部网关不在客户快照内；另有 `scripts/package.mjs` 分发各平台打包命令 |

## 2. 客户端可以独立给 DMG/EXE

可以，而且当前 Community 分支已采用服务器与桌面分开启动的方式。

建议交付内容：

| 交付物 | 安装/运行位置 | 内容 |
| --- | --- | --- |
| 服务器镜像 | 客户服务器 | API、选定 IM 的服务端实现、后台任务、实时协作、需要的后台与分享 Web；单镜像方案再包含 PG/Redis |
| macOS DMG | 员工 Mac | Electron 桌面应用，按目标架构生成 |
| Windows 安装 EXE | 员工 Windows | Electron 桌面应用，按目标架构生成 |
| 配置与交付记录 | 客户部署目录/运维留档 | 地址、挂载目录、版本、组件选择、初始化与备份升级步骤；真密钥另行安全保存 |

注意三件事：

1. **不能拿任意 SaaS 安装包直接发。** 客户包必须连接客户的 API、IM、协作与分享端点，并选择匹配的 IM 实现；更新、诊断上传等也要遵循交付策略。
2. **第一次安装与自动更新是不同产物。** DMG/EXE 足够人工安装；若启用自动更新，还需要更新清单及对应 ZIP/blockmap 等制品。可以先明确采用人工升级。
3. **镜像里可选托管安装包下载。** 将 DMG/EXE 放进下载目录只是文件分发，不代表客户端在 Linux 容器内运行。更适合独立制品目录或挂载卷，避免每次客户端升级都重建服务端镜像。

客户版现成的[Community 端点模板](https://github.com/larchiveai/TabTin/blob/d89273293bc22e14f461ba870eb2bfff89b284f9/apps/tabtin-electron/.env.community.example)和[打包脚本](https://github.com/larchiveai/TabTin/blob/d89273293bc22e14f461ba870eb2bfff89b284f9/apps/tabtin-electron/scripts/build-packaged-app.sh)值得复用设计：注入公开端点，清空官方 Sentry 设置，未配企业更新源时关闭自动更新。客户包也要确定签名、公证及安装身份，不能把客户版现有的临时打包行为直接当作正式分发标准。

## 3. 建议的同源装配方式

```text
打包页面：版本 + 客户地址 + IM + 存储 + 登录 + 客户端平台
                         ↓
                  校验并保存交付配置
                         ↓
           固定同一个源码提交，解析组件与依赖清单
                    ↙             ↘
       Linux 服务端构建          Mac / Windows 构建机
       生成服务器镜像             生成 DMG / EXE
                    ↘             ↙
             同一交付编号、配置摘要、兼容性记录
                         ↓
               组合验收通过后交付给客户
```

页面可以使用勾选框；为了让“不勾选”仍意味着有聊天能力，更建议显示“聊天服务：内置 IM / 腾讯云 IM”和“文件存储：服务器本地 / 阿里云 OSS”这样的明确选项。

交付配置的示意（只是建议字段，当前未实现）：

```json
{
  "schemaVersion": 1,
  "sourceCommit": "<固定提交>",
  "deployment": "private",
  "imProvider": "builtin",
  "storageProvider": "local",
  "serverBundle": "all-in-one",
  "desktopTargets": ["mac-arm64", "win-x64"],
  "publicBaseUrl": "https://tabtin.customer.example",
  "desktopUpdatePolicy": "manual"
}
```

先做有限字段的配置解析器和可打印的构建计划，再让页面调用它；不需要先建设通用插件平台。服务端构建、客户端构建和验收都读取这份记录，不各自维护同名开关。保留默认 SaaS 配置及现有对外 API 契约。

将三类输入分清：

- **打包选择**：包含哪些 Provider、SDK、服务和桌面平台，决定制品内容。未选的腾讯客户端 SDK 应通过构建入口排除并检查产物，不能只在运行时不调用。
- **部署配置**：客户可达域名、存储目录、凭据与证书，在安装时注入。真密钥不进镜像层、DMG、EXE或交付公开清单。
- **运行能力声明**：服务端告诉客户端本部署支持的 IM/存储及协议能力；应作为可加性信息，让旧 SaaS 客户端继续工作。新客户端校验匹配后进入业务流程，不能两边各自猜默认值。

页面选项应先限定为“新部署/新交付配置”。已有环境从腾讯改内置 IM，或从 OSS 改本地存储，涉及历史消息、对象和引用迁移，不能当作随时可切的普通偏好。首版可以不提供跨 Provider 热切换。

## 4. IM 是主要工程难点

现有两个版本是两种单实现，而不是已经可并存选择的双实现：SaaS 的类型和 Registry 锁腾讯；客户版锁 Django。当前 SaaS 还增加了主进程腾讯数据面，不能只复制 `djangoProvider.ts` 就算完成。

建议复用现有 `IMProvider` 业务接口作为起点，对照两端契约，隔离提供方特有的消息定位、已读/未读、事件、编辑撤回、附件、Reaction、成员目录、群聊 @Agent 等行为。先补齐完整业务路径再做打包裁剪，避免大量 `if community` 散落到 UI。

| 打包选择 | 服务端仍需包含 | 客户端应接入 |
| --- | --- | --- |
| 腾讯 IM | 当前 Go `tabtin-im-control` + 它需要的数据库/配置；业务身份、会话成员、Agent 触发仍由 TabTin 管理 | 腾讯 Provider/SDK 与匹配控制服务 |
| 内置 IM | 明确受维护的内置消息 API、持久化和实时事件实现；以客户分支 Django IM 为迁移评估依据 | 内置 Provider、Django API 与对应事件链路 |

**选腾讯不等于删掉所有 TabTin IM 服务。** 腾讯托管的是消息相关能力，当前 Go control 仍是业务必要组件，详见[IM 部署说明](/Users/yang/Documents/larchiveai/TabTin/apps/tabtin-im/docs/server-deployment.md)。

内置方案在实现前应明确其维护边界。当前 SaaS 正典已废弃 Django IM；此次用户明确提出的是让同源产品支持内置 IM。应为私有部署划定并测试受支持的内置实现，不把 SaaS 运行时改成腾讯/Django 双读、双写、失败自动回退。正式进入实现时同步记录这一新增交付边界。

对已有客户 `private/260907` 的升级，另建真实数据库样本和版本兼容验收；不能默认它与最新 SaaS schema 和客户端接口一致。

## 5. OSS 开关可复用，但不是全部工作

SaaS 已有 `SERVICES_OSS_PROVIDER=local/aliyun`，这是良好入口。客户分支还有本地文件卷、共享密钥卷、公共地址验证等可提取改进；但 `IS_COMMUNITY_EDITION` 下强制 local 的逻辑不应直接照搬到需要自由组合的私有产品。

本地模式必须保证：

- API 与后台任务使用同一持久化对象目录；容器替换后附件仍在。
- 返回客户电脑能访问的地址，不能返回容器内部 DNS 或只在服务器成立的 `127.0.0.1`。
- 私有访问、预签名、预览、协作文档媒体、导入导出与大文件均验收；SaaS 中 local 仍有开发用途标注，存在开关不代表所有生产场景已经验过。
- 业务代码中的直接阿里云调用纳入扫描，不能只核对通用工厂。
- 文件存储与桌面更新存储分开处理：当前 `get_updater_oss_service` 明确不支持 local provider，不能因附件用本地就假定企业自动更新也已完成。

登录同理：关闭短信只解决云依赖，不自动提供可用的注册、邀请、账号恢复流程。客户版固定验证码是单独配置，企业交付须选定实际认证方式；不在本轮直接决定密码、邮箱或 SSO 方案。

## 6. 单镜像能做，先保持业务模块可拆

可以提供真正单镜像：固定 PG 主版本，内部进程管理器管理 PG、Redis、API、任务调度、协作/实时与选定 IM 服务；有序启动、逐项就绪检查、独立日志与优雅停止；将数据、附件、安装密钥放在镜像之外。

这层装配应复用同样的服务产物和 Provider 配置，而不是改业务逻辑去适应同进程运行。镜像包含多个进程，并不表示它们必须合并成一个程序。

建议分两步落地：

1. 先在现有 Compose 形态证明各选项下的服务端和客户端能跑通，这用于开发与组合验证。
2. 若“交付一个镜像”是确定要求，再将相同服务产物装进一体镜像，并验证重启、故障、数据迁移和恢复。仍然单独提供 DMG/EXE。

替代方案是“一个离线安装包包含多个镜像 + Compose + 启动器”，也能做到一条命令安装，通常更容易独立维护数据库。它和真正单镜像不是同一交付物，不能未经产品确认就互相替代。

当前客户 `compose.yaml` 是本机模式，`compose.lan.yaml` 还有具体局域网地址；它可以参考，不能原样作为通用企业部署模板。

## 7. 合代码与打包平台怎么处理

推荐：后续功能与修复继续进入目标 SaaS release，从固定提交按交付配置生成变体。客户分支作为历史交付参考，不承担持续功能开发。

客户分支包含大量公开快照裁剪、端点替换、工具与文档删除，以及 Community 专用修改。整分支合回会把与私有部署无关的变动一起带入。应按能力提取：内置 IM、存储完善、初始化与凭据、桌面发行配置，每一项都在同一源码中具备默认 SaaS 行为与私有行为的验证。

打包平台复用[现有 Console/Runner](/Users/yang/Documents/larchiveai/TabTin/tools/tabtin-pack-gateway/README.md)：

- 网页新增私有交付配置和解析后的制品清单。
- 服务端新增“构建客户交付物”的独立动作；不复用当前会推送云效并更新 ACK 的部署动作。
- Mac/Windows Runner 按同一个提交和配置构建客户端；保留现有签名、架构、状态、日志和制品管理能力。
- 现有客户端 `channel=stable → profile=production` 不能代替私有部署身份；发行渠道、客户部署类型、Provider 选择应彼此独立。
- 并发打包时使用既有构建隔离/锁，避免用客户参数覆盖公共 `.env.production` 污染下一次 SaaS 打包；同提交、同选择可复用产物，客户特定地址和密钥尽量留在安装配置层。

建议第一阶段先产出可复查的构建计划，不立刻编译所有平台：提交号、组件、端点、数据目录、缺失配置、目标安装包、镜像标识、验收组合。CLI 入口先跑通，页面只负责填表与展示结果。

## 8. 最小验收矩阵与推进顺序

IM 两种 × 存储两种，共四种核心组合应有共同验收；保留 SaaS 默认组合回归。短信、更新等后续选项按实际支持范围增加验证，不宣称任意组合都成立。

每个组合验证：两个真实用户登录 → 建群与消息收发 → 历史及未读 → 编辑/撤回与必要交互 → @Agent 回复 → 文件上传/下载/预览 → 文档协作 → 重启保留数据。检查实际出站连接，证明未选的提供方既未被调用，也未作为启动必填依赖；若要求从制品剔除，则另查依赖清单及产物。

机器断言需包含：客户端/服务端 Provider 一致、关闭云服务时无对应外连、组件按计划装入、初始化失败不可报交付成功、附件持久卷可恢复、服务端版本与客户端兼容范围可查。错误凭据时明确失败，不自动转向另一家服务。

推荐先后次序：

1. 定义交付配置与客户端/服务器边界。
2. 在同一 SaaS 源码中完成一个内置 IM + 本地存储的私有闭环，同时验证 SaaS 原行为。
3. 对齐另外两个混合组合，完善关闭短信后的登录体验。
4. 接入现有打包页面和各平台 Runner，形成同一次交付的制品集合。
5. 完成服务端单镜像与恢复/升级演练；已有客户数据升级单独验收。
