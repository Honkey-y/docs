# is-admin 压测慢：PostgreSQL 链路分析

分析日期：2026-10-30。已知现场使用 PostgreSQL；尚无客户部署版本、完整请求 URL、原始耗时日志、PG 执行计划与连接池指标。以下区分代码事实与现场假设，不把本地代码版本当作客户实际版本。本次未修改业务代码、未操作客户数据库。

## 结论

1. 与电子表格截图相符的主链路是 `deep-table-server → space-server /api/space/user-info/check-user/is-admin → system-server /user-permission-info → Redis / 账号中心与权限表`。它不是直接查询一个 user 表的简单接口。
2. **PG 有可定位的历史漏建索引问题**：初始脚本在不同表上复用索引名，并使用 `CREATE INDEX IF NOT EXISTS`。PG 索引名在同一 schema 内不能重复，因此后续目标表可能被跳过。仓库已有 `V2.14.5.1.2__same_index_to_different.sql` 补救，明确包含 `sys_user_role_pk`、`user_enterprise_pk`、`user_group_user_pk`。优先检查现场实际索引及迁移记录。
3. **“开启缓存后改善，后来又慢”有代码层面的解释**：默认 TTL 30 分钟，命中不续期；GROUP 变更消息清全部权限缓存；缓存按用户、空间、应用区分；未命中没有合并并发回源。过期、清缓存或换用户/空间/应用后，慢链路会重新暴露，可能继续压满数据库连接池。
4. 不能据此定案为“user 表没索引”或“表被打满”。缺索引、查询范围大、缓存失效、JDBC 连接等待、服务线程/HTTP 等待可以同时存在，甚至构成因果链。

## 主链路与证据

### 1. 电子表格同步等待管理员判断

- `deep-table-server/.../WorkbookManageServiceImplV2.java:1858` 的 `queryWorkbookDataV2` 在开头 `1862` 调用 `elementService.checkIsAdmin(...)`，随后才执行区域取数 `multiQueryDataInSheet`。管理员查询是前置串行依赖。
- `deep-table-server/.../ElementServiceImpl.java:597` 拼出空间服务 URL，同步 `HttpUtil.getForResponseResult`。
- `ElementUrlConstans.java:52` 指向 `/api/space/user-info/check-user/is-admin`。
- `HttpUtil.java:67` 的 HTTP 拦截器记录 `url === ..., rt == ...ms`。它计时 `execution.execute`，不等同于数据库执行时间，也不保证包含完整响应体反序列化。

### 2. 空间服务再同步调用系统权限服务

- `space-server/.../SpUserInfoController.java:240` 的 `validUserIsAdmin` 调 `queryUserIsAdminOrNot`。
- `SpUserInfoServiceImpl.java:768` 读取当前 app，然后调用 `SystemInfoCloud.getUserPermissionInfo`，最终只取权限对象的 `appAdmin`。
- `SystemInfoCloud.java:64` 的方法构造 `systemUrl + /user-permission-info?userId=...`，使用同步 RestTemplate；传递 space/app。已有 `user-permission-info接口 cost` 日志。
- 原来直接查询 `sp_user_info.admin_tag` 的实现目前是注释代码（`SpUserInfoServiceImpl.java:778` 后）。因此若“user 表”指这个旧空间用户表，不能直接认定它是当前调用的慢 SQL。它的 PG 初始化脚本也声明了 `(user_id, space)` 主键。

### 3. 系统权限服务先尝试缓存，未命中再做完整计算

- `system-server/.../UserRoleController.java:671` 传 `userDetailDto=null, flag=true`，满足缓存读取条件。
- `UserRoleServiceImpl.java:950`：实际读取条件是开关开启、没有预传用户详情、flag 为 true。
- key：`userPermission:<userId>:space:<space>[:app:<app>]`；不是一个用户只有一条缓存，app 缺失和 app 有值也不是同一 key。
- 默认配置 `USER_PERMISSION_CACHE_OPEN=false`、`USER_PERMISSION_CACHE_EXPRESS_MINUTES=30`。
- `seepln-redis/BaseRedisRepositoryImpl.java:39` 带 TTL 写入，`:45` 只有 GET；命中没有刷新 TTL。
- 未命中按顺序计算并写回，没有围绕同一 key 的 single-flight/互斥。相同 key 的并发冷请求可各自查库。
- GET 异常未在此方法捕获；写缓存异常被捕获后仍返回权限结果。持续写失败会导致后续持续未命中。不能把 Redis 读异常描述为这里自动降级查库。
- `RoleManage.clearCacheAll` 扫描并删除全部匹配权限 key；`UserRoleConsumerMessageActuator` 收到 `type=GROUP` 调该方法。当前源码用 SCAN，仍需核对客户版本。

### 4. 回源计算并不只查用户主表

`getUserPermissionInfoWithRealTime` / `checkSystemAdmin`：

1. `sys_space_info` 按空间查询 tenant code。
2. 调账号中心 `/s/user/group/enterprise/get-user-detail` 获取企业角色、用户组及父级组。
3. 账号中心 `roleAndGroupByUser` 查询 `user_enterprise_pk LEFT JOIN user_group`；查询 `sys_role / sys_user_role_pk`；查询启用用户组、组父子关系、用户所在组并计算父级关系。
4. 系统服务检查 `user_group_space`、查询 `user_group_role JOIN role_info`。
5. 非空间管理员按角色查 `role_permission / permission_info`；部分应用用户还查 `create_element_info JOIN create_element_info_permission` 的 COUNT。
6. 企业管理员、空间管理员和无角色用户存在不同的提前返回路径，压测账号角色不同会改变 SQL 数量。

特别值得优化的是：账号中心 `UserInfoServiceImpl.roleAndGroupByUser` 先调用 `getEnableEnterpriseSpaceUserGroupList(enterpriseId, null)` 和 `getEnterpriseSpaceUserGroupParentPkList(enterpriseId, null)`，加载整个企业各空间的数据，再把 `spaceIdList` 收窄到当前空间。即使有索引，大企业的数据传输、对象创建和组关系计算仍可能昂贵。建议先测返回行数与 CPU，再在验证组关系语义后下推空间过滤。

## PG 索引判断

关键证据文件：

- `/Users/yang/deepfinance_project/seepln-account/seepln-account-server/src/main/resources/db/migration/postgresql/V1.0.0__Initial_ddl.sql`
- `/Users/yang/deepfinance_project/seepln-account/seepln-account-server/src/main/resources/db/migration/postgresql/V2.14.5.1.2__same_index_to_different.sql`

例如初始脚本先在 `platform_role_user_pk` 创建 `index_pr_user_id`，再尝试同名索引给 `sys_user_role_pk`、`user_enterprise_pk`、`user_group_user_pk`。在同一 schema、按脚本顺序初始化时，后者可能没有对应的 user_id 索引。补救脚本改用 `_urp`、`_etp`、`_gup` 后缀。

这比“user 主表没索引”更具体，也更符合回源 SQL。PG 初始脚本中的 `user_info` 有 `PRIMARY KEY(id)`，用户名、手机、邮箱也有索引声明；`status` 索引则在补救脚本中另有修复，但本次核心角色/组查询不是靠它驱动。

| 对象 | 当前代码/脚本线索 | 现场优先核对 |
|---|---|---|
| `sys_user_role_pk` | 按 user_id 查角色；历史 user_id/role_id/enterprise_id 索引重名 | 是否真有有效索引、扫描行数与过滤比例 |
| `user_enterprise_pk` | user_id + enterprise_code 过滤；历史重名 | user_id 索引及真实执行计划 |
| `user_group_user_pk` | 按 user_id 找当前空间的组；历史重名 | user_id 索引及与 user_group 的连接成本 |
| `user_group_parent_pk` | 脚本主要声明 id 主键；代码按 enterprise_id 加载 | 行数、是否缺过滤索引、是否可下推 space |
| `sys_role` | 企业/角色/启用状态过滤，初始主要为 id 主键 | 表是否足够大到值得补联合索引 |
| `user_group_role` | 主键 `(space,id,type,role_info_id,app)` 已存在 | USER/GROUP OR 与 IN 的实际计划，不能直接说无索引 |
| `user_group_space` | 主键 `(id,type,space)`，本次条件覆盖这些列 | 实际主键、类型匹配、计划 |
| 元素权限相关表 | COUNT 分支才访问 | 是否实际走到该分支，扫描量与耗时 |

先按实际谓词与执行计划补缺失索引，不预先对所有表堆联合索引。`Seq Scan` 在小表或高命中比例下可能是正确计划；“有顺序扫描”本身不是慢因证据。Flyway 成功记录也不能替代 `pg_index.indisvalid/indisready` 与实际索引定义核验。

## 第二次变慢：如何快速区分

| 同一慢请求的观测 | 优先解释与下一步 |
|---|---|
| 大量 `from db start`，少量 `from cache` | 检查运行实例开关、key 维度、TTL、全量清缓存消息、Redis 淘汰与写失败 |
| 约 30 分钟后成批出现 DB 回源 | 核对实际 TTL；相近预热时间可能形成集中到期，需 key 级数据确认 |
| GROUP 消息/`begin to clear all cache` 后恶化 | 全量失效后并发重算是高优先级假设 |
| `from cache cost` 本身就很大 | 查 Redis 延迟、客户端连接、网络、序列化、应用停顿；不是权限回源 SQL |
| 缓存 cost 很小，空间服务调用 cost 很大 | 查空间→系统的 HTTP 等待、系统入口排队/拦截器、返回处理与写缓存；该 cost 不覆盖全部接口 |
| `from db end cost` 很大 | 它包括 Redis GET 及整个回源计算，不能当作单条 SQL 时间；继续看账号接口及 SQL 分段 |
| SQL 单次执行很快，但 JDBC pending 上升 | 连接池等待或连接被其他业务占用；盲目加索引/扩连接数不能保证解决 |
| PG active 查询多、CPU/IO 高且扫描大量行 | 慢 SQL/缺索引/范围过大导致资源饱和，缓存失效可能是触发器 |
| PG wait_event_type=Lock | 查看 `pg_blocking_pids`，确认 DDL/长事务等实际阻塞者 |

PG 普通 SELECT 不会因为普通行更新锁就必然被阻塞；通常 MVCC 可读旧版本，但仍可能等待表级强锁等。接口主要读库，不会自行把 user 表写满；若“打满”指存储空间满，需要磁盘/错误证据；若指连接、CPU、IO 饱和，需要对应指标。

## 下一轮压测最小取证方案

1. 确认完整 URL、部署版本/镜像、PG 版本、实际空间与 app header、用户角色、每个系统实例的有效缓存配置。
2. 固定一个真实 user/space/app，连续请求验证先回源后命中。随后观察实际到期和正常失效事件；不要在生产人为清全部缓存制造峰值。
3. 从同一 trace 收集：电子表格 HTTP rt、空间服务 `user-permission-info cost`、系统 `from cache/from db` 日志、账号 `/s/user/group/enterprise/get-user-detail` 耗时。跨服务不保证 TID 被传播，必要时加 traceId/user/space/app/实例关联。
4. 同时抓 JDBC active/idle/max/pending/获取连接耗时、服务线程、HTTP 连接等待、Redis hits/misses/expired/evicted/command latency、PG 活跃会话/锁等待/CPU/IO。Redis 全局 hit rate 会混合其他缓存，需结合本权限前缀日志。
5. 运行同目录[只读诊断脚本](只读诊断.sql)的只读目录与统计查询，确认漏建索引、无效索引、迁移记录。账户库和系统库若分离，要分别连接执行；PG 不能直接用 MySQL 式跨库限定名。
6. 对实际慢 SQL 用真实参数取 `EXPLAIN (ANALYZE, BUFFERS)`，记录 rows、loops、Rows Removed、Buffers 和执行耗时；ANALYZE 会真正执行查询，建议在可控窗口单条执行。对照应用日志区分执行时间与连接等待。

修复顺序：先证实并补齐现场缺失索引 → 收窄企业级组查询/减少不必要计算 → 处理同 key 并发回源、TTL 集中过期和全量失效范围 → 依据池与主机指标处理容量问题。缓存优化必须保留权限变更失效语义，不建议仅无限延长 TTL。

## 范围与版本差异

主要沿独立 `deep-table-server / space-server / system-server / seepln-account` 仓库追踪，另对照合并仓库 `deepfos-platform`：后者把若干 HTTP 调用改成 `SystemApi / AccountApi` 内部调用，但权限缓存和角色/组查询的核心逻辑相近。客户版本未确认，不能把远程调用/内部调用的部署形态混为一谈。

前端成员页另有 `/api/space/is-admin`：它在账号控制器先检查企业管理员，再调用权限逻辑。该入口的前置查询不受上述权限缓存覆盖，但它不是已找到的电子表格后端调用路径。网关是否参与内部请求取决于现场服务地址和路由，不应无依据叠加网关耗时。

可向领导汇报：**“权限接口的慢点已收敛到完整权限汇总链路，PG 存在历史索引重名漏建的明确线索。开启缓存只减少回源次数；到期、全量失效或 key 变化后，关联表查询与企业级用户组计算会重新发生。需要用现场索引、缓存命中与同一请求的 SQL/等待耗时定案，暂不能简化成 user 主表没索引。”**
